## 2024-07-30 - Fallback Secret Exposure
**Vulnerability:** The ComplianceLedgerService hardcoded a fallback private key if the `APP_ENV` environment variable was not set, allowing production environments to default to a known weak key if misconfigured.
**Learning:** Security configurations must fail closed. When handling environment-specific security settings like private keys, the application should throw an exception if the required variables are missing, rather than silently falling back to a hardcoded testing key unless explicitly running in a verified 'testing' environment.
**Prevention:** Always use strict environment checks (e.g., `getenv('APP_ENV') === 'testing'`) before allowing fallback logic. Default to throwing `\RuntimeException` for missing security configurations in all other cases.
## 2024-05-24 - Compliance Ledger Hard-Coded Secret Fallback
**Vulnerability:** The ComplianceLedgerService fell back to a hard-coded secret ('compliance-fallback-secret-key-12345!@#') if the COMPLIANCE_PRIVATE_KEY environment variable was missing, unless explicitly in testing/development environments (but logic allowed it if APP_ENV was simply empty/unset).
**Learning:** Fallbacks for cryptographic keys are extremely dangerous if they can be inadvertently triggered in production (e.g., due to a missing environment variable). Production systems should "fail closed" (throw an exception) when critical secrets are missing, rather than proceeding with a known/weak secret that compromises data integrity.
**Prevention:** Ensure cryptographic key retrieval logic strictly requires the key to be present and only allows mock/fallback keys when the environment is explicitly, incontrovertibly set to 'testing'. Do not allow fallbacks on empty or unset environment states.
